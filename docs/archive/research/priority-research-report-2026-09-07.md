## 7. 向其他成员添加滴答待办

### 官方接口核对

滴答官方开放文档说明，创建任务使用 `POST /open/v1/task`，`title` 和 `projectId` 是必填字段，`startDate` 与 `dueDate` 均没有标注必填。因此，可以通过省略日期字段来创建无日期待办。这一判断来自接口文档，本轮没有向任何真实账户写入测试任务。[S1]

授权凭证对应具体用户，调用接收者账户的创建接口必须使用接收者的有效授权。项目已经将滴答凭证按身份加密保存，但现有 `accessToken()` 始终读取当前登录者的凭证，不能直接复用当前新增接口向另一个人写入任务。现有任务列表还会过滤无日期任务，因此即使创建成功，它也不会自然出现在“今天／七天”的列表中，这个显示问题需要与新增流程一起处理。

### 推荐方案与待确认事项

建议每位接收者在连接滴答时指定一个用于接收房间待办的清单，并单独启用“允许房间成员向我新增待办”。服务器保存目标身份与清单的对应关系，新增时核对双方身份和授权，仅向滴答提交标题、目标清单及必要的时区信息，省略日期。权限检查不得依赖客户端传来的昵称或按钮是否可见。

| 需要确定的事项 | 推荐默认方案 | 需要确认的原因 |
| --- | --- | --- |
| 每位成员的目标清单 | 接收者自己指定已有清单 | 需求没有指定清单，官方创建接口又要求 `projectId`；不能任意选择某人的私人清单 |
| 哪些成员可以向接收者新增 | 接收者启用后允许同房间已登录成员新增 | 现有登录与滴答连接没有区分“本人管理”和“代他人新增”的授权范围 |
| 无日期任务的显示位置 | 在本人新待办弹窗中呈现，并增加无日期任务入口 | 现有“今天／七天”查询排除了无日期任务，创建结果容易被误认为没有送达 |

完成上述约定后，建议建立专用的跨用户新增接口，与本人任务完成接口分离。请求携带唯一操作标识，服务器记录发起者、接收者、滴答返回的任务标识及处理状态；遇到超时后应先核对创建结果，避免用户重试时重复创建。不要把滴答令牌发送给其他成员的浏览器。

**处理状态：已调研未实现，并待用户确认上述业务约定。** 不使用猜测出的清单标识，也不调用真实账户进行试写。

## 9. 新待办提醒的前置条件

提醒需要以第 7 项创建成功后产生的服务器记录为依据，不能仅依靠房间广播，否则离线成员会漏掉提醒。建议记录以接收者身份分组，浏览器只获取本人未读记录；“新”按钮打开时固定本次展示的记录集合，关闭后只标记这一集合为已读，从而保留弹窗打开期间新增的未读任务。

第 7 项确定目标清单和成员授权后，可以同时实现此记录结构及提醒界面。**本项待用户确认第 7 项的业务方案，暂未实现**；已读状态按用户维护这一要求本身已经明确，无需再次询问用户是否改为按设备维护。

## 10. 图标与美术资源

### 授权与现状

项目已经安装 `lucide-react`，部分房间按钮和画板工具也已使用它，继续采用同一套资源能减少混用。Lucide 官方许可页允许使用、修改和分发，包括收费用途，但要求保留版权与许可声明；部分来自 Feather 的图标适用 MIT 许可，应同时保留随包分发的相关声明。本轮也核对了已安装包中的 `LICENSE`，无需新增图标库。[S2]

### 统一规则

建议常用功能图标采用 20px 的显示尺寸及 1.8 至 2px 的描边，紧凑消息操作可使用 18px 图标。图标按钮的点击区域独立于图形尺寸，移动端主操作至少保留 44px 的触控区域；选中状态用背景和颜色共同表示，并为键盘焦点提供可见边框。工具提示只描述动作，保留对应的 `aria-label`。

| 现有入口 | 建议图标 | 悬停文字 |
| --- | --- | --- |
| 聊天附件加号 | `Paperclip` | 添加附件 |
| 成员／画板卡片中的“板” | `Presentation` | 查看画板 |
| 任务范围切换的自画图形 | `CalendarDays` | 切换任务日期范围 |
| 文件夹与文件的字符图形 | `Folder`、`File` | 打开文件夹、查看文件 |

这份映射表属于后续全站替换方案。第 13、16 项新增或修改的局部按钮已采用 Lucide，但其余既有字符图形尚未全部替换，不能据此宣称全站图标统一已经完成。

**处理状态：已调研未实现。** 建议先逐项替换功能入口，再统一按钮尺寸和状态样式；不建议为了几处入口另行安装风格相近的第二套图标库。

## 12. 持续摇铃

### 可确认的浏览器能力

MDN 说明 `navigator.vibrate()` 需要用户先与页面交互；不支持震动硬件或接口的设备可能没有效果，过长的震动序列会被截断，实际限制由浏览器实现决定。传入 `0` 可以停止当前设备当前页面发起的震动，但接口没有用于控制另一部手机或另一块手表的参数。[S3]

WebKit 官方说明，iOS／iPadOS 16.4 起，添加到主屏幕的 Web App 可以在用户主动操作后申请 Web Push 权限，通知能够出现在锁屏和配对的 Apple Watch 上，同时受专注模式等系统设置管理。这证明了通知送达途径，不能据此推导出网页可以让 Apple Watch 持续震动到发起人按下停止。[S4]

| 接收环境 | 可利用的途径 | 对本需求的限制 |
| --- | --- | --- |
| Android 前台网页 | 支持时调用 Vibration API | 需要用户交互，震动序列有限；页面退出前台后的持续执行无法保证 |
| Android PWA 与系统通知 | Web Push 和通知渠道 | 普通通知的震动由系统及渠道设置决定，无法保证无限持续或立即远程停止 |
| iPhone 主屏幕 Web App | Web Push，用户授予通知权限 | 可以收通知，但不存在可直接满足本需求的跨设备持续震动网页接口 |
| Apple Watch | 配对 iPhone 的通知呈现 | 呈现与震动受系统设置控制，不能由网站规定持续时长 |
| Wear OS／三星 Galaxy Watch | 手机通知转发或配套原生程序 | 单靠网站不能控制手表震动循环，需要针对手表应用和系统版本验证 |
| 华为、小米等手表 | 厂商配套应用的通知同步 | 本轮未获得能让任意网站持续控制震动的统一接口证据，须按具体型号与系统分别验证 |

### 推荐设计

如果保留“所有接收设备持续提醒，发起人点击后停止”的验收要求，需要先明确实际手机与手表型号，并评估配套原生程序；不能把反复发送普通推送包装成持续来电。原生方案还必须遵守系统对后台运行和通知的限制，不应借用仅面向真实通话的权限来伪装学习提醒。

无论最终采用何种客户端，服务器都应维护单个摇铃会话，包括唯一 `ringId`、发起者和目标成员，以及递增版本、开始时间与结束时间。接收端按 `ringId` 去重，只更新现有提醒；停止状态必须保存在服务器，离线恢复后先读取当前状态，过期的开始事件不得重新触发提醒。还需要设置最长持续时间，防止发起人退出后提醒一直存在。

**处理状态：已调研未实现。** 当前纯网页形态不能满足需求所描述的跨品牌持续震动保证；如接受“前台网页短时震动＋后台一次通知”，应明确将其作为另一种产品方案，不与持续摇铃混同。

## 14. 语音转文字

### 调用方式与报价

官方文件转写文档提供 `/v1/audio/transcriptions`，通过上传完整录音获得转写结果，当前文档推荐普通录音优先评估 `gpt-transcribe`。文档列出单文件上限 25MB，并支持 `webm`、`m4a`、`wav` 等常见格式；若浏览器生成的格式不在服务支持列表中，需要先做兼容处理。[S5]

以下为本轮读取的官方定价页面所列估算单价，单位为美元，按音频分钟数计算预算；页面对相应模型还列出 token 计费说明，因此表内金额应作为预算估算，不等同于承诺的账单金额。[S6]

| 候选模型 | 页面所列每分钟估算 | 60 分钟估算 | 1,000 分钟估算 |
| --- | --- | --- | --- |
| `gpt-transcribe` | $0.0045 | $0.27 | $4.50 |
| `gpt-4o-mini-transcribe` | $0.003 | $0.18 | $3.00 |
| `gpt-4o-transcribe` | $0.006 | $0.36 | $6.00 |

本轮没有调用付费识别接口，没有产生识别账单，也没有上传项目中的私人语音。账户与地区可用性、付款条件以及最终税费应在实际接入前核对，不通过更换地区或账户规避服务限制。

### 中文效果与服务器负担

支持中文与适合本项目是两个不同的评估环节。当前缺少经过允许用于测试的代表性录音，因此没有给出未经测量的中文准确率；后续应使用普通话、带口音讲话及中英文术语混用的片段进行对照，重点检查人名、算法名称与数字，另行记录安静环境和噪声环境下的错误情况。

云端文件识别使项目服务器主要承担文件读取与上传、任务排队和结果保存，CPU 负担通常比本机运行识别模型小。自行部署开源识别模型可以避免按分钟向服务商付费，但会增加模型文件、运行内存及 CPU／GPU 的需求；本轮没有测量现有服务器运行识别模型时的负载，不能将其称为零成本方案。浏览器识别接口的兼容性与服务依赖也不足以支撑所有历史录音统一转写。

建议先保持本轮已实现的录音、发送与历史播放功能独立运行。后续若接入转写，应采用用户主动点击、后台异步处理的方式，按附件内容与模型版本缓存结果，限制并发并设置月度费用上限；失败时保留原录音，不影响消息发送。收费账户、样本效果和预算上限确认前，不启用自动转写。

**处理状态：已调研未实现。** 已给出可调用接口、当前报价与评估方法；中文实测、服务可用性和预算条件尚未完成验证。

## 15. 网易云音乐播放状态同步

2026-09-10 更新：用户已取消独立音乐模块及其后续同步需求，以下内容仅为历史调研。当前声音分享使用已有投屏电脑音频功能，见[移除记录](../2026-09/task-workflows.md#2026-09-10审批版本规则与音乐范围)。

### 官方能力与社区证据

本轮检索没有找到由网易云公开承诺、可直接返回任意用户桌面客户端当前播放曲目、暂停状态和播放进度的官方接口。歌曲目录、历史播放和正在播放属于不同信息，不能用歌曲查询接口或最近播放列表代替实时状态。

微软的 `GlobalSystemMediaTransportControlsSessionManager` 能读取已经接入系统媒体控件的播放会话，自 Windows 10 1809 起提供相应能力。它是 Windows 系统接口，需要本机程序访问，并要求目标播放器实际发布会话信息；系统 API 的存在本身不能证明某个网易云版本提供了完整进度数据。[S7]

社区项目 now-playing-service 的 issue #39 记录了网易云拖动进度条后没有同步的情况。维护者解释早期进度由内部计时器模拟，随后讨论了通过 C# 读取窗口界面补充进度同步，并提到当时准备在后续版本发布。该讨论也记录了插件方式的兼容性问题；本轮没有验证讨论中的修复是否在用户使用的发布包中可用，不能把“议题已关闭”视为本项目已经通过验收。[S8]

### 路径比较

| 路径 | 曲名与歌手 | 播放／暂停与进度 | 安装和维护成本 |
| --- | --- | --- | --- |
| 自习网站直接读取网易云网页 | 受同源限制，无法任意读取另一个网站 | 不能直接读取另一个网页的播放器状态 | 无安装成本，但无法满足要求 |
| 网易云网页上的浏览器扩展 | 可在明确授权的页面读取可见播放信息 | 可观察页面播放器；网页结构变化后需适配 | 需要安装扩展和限定站点权限，依赖用户已登录且打开网页 |
| Windows 本机程序读取 SMTC | 播放器公开这些字段时可读取 | 是否有准确进度取决于播放器版本 | 需要安装小程序及受控的本地到网站通信，先检测实际会话 |
| 本机程序读取窗口界面 | 可利用界面已显示的信息 | 社区有读取进度的实现线索 | 依赖窗口结构，升级或最小化等状态可能影响读取 |
| 客户端插件／非官方接口 | 取决于插件和接口能力 | 能力及维护状态不一致 | 登录依赖、更新失效和账户风险较高，不作为默认方案 |

推荐先对用户实际使用的桌面版本做只读能力检测：如果系统媒体会话确实提供所需字段，就优先采用本机小程序只上传状态；如果只提供曲名而没有可靠进度，应明确显示“进度不可用”，不要用计时估算冒充准确数据。网页使用者可另行选择限定在网易云域名内的扩展，避免要求扩展读取所有网站。

同步数据建议包括歌曲标识、标题与歌手、播放状态、当前进度、总时长，以及观察时间和递增序号。服务器拒绝旧序号，客户端在收到停止或失联信息后停止推算进度，并显示来源及过期状态。只传这些必要字段，不上传登录 Cookie、账户令牌或播放器内存。

**处理状态：已调研未实现。** 需要先确认主要使用网页还是桌面客户端，以及是否接受安装扩展或本机程序；随后对实际网易云版本做只读检测。本轮未安装插件，也未直接控制 Windows 上的音乐客户端。

## 17. 全站视觉设计

### 参考与项目现状

Linear 的官方改版文章介绍了如何调整侧栏、页头和面板，降低视觉干扰并保持对齐，也说明了通过主题变量统一不同表面的颜色、强调色与对比度。这些方法适合本项目的任务与协作界面；其产品导航和业务结构则不应直接移植到自习室。[S9]

Radix Themes 的配色文档说明了颜色梯度、透明色及语义映射，并将键盘焦点和选中颜色与组件强调色关联。可借鉴这些规则来建立项目自己的 CSS 变量，不需要为视觉改版整体更换现有组件技术。[S10]

本项目已有粉、蓝、绿、紫主题和自定义背景，但样式中仍有多处固定粉色值，以及多轮叠加的字号和组件覆盖规则。现有功能布局应继续围绕共享画面与右侧聊天／任务区域组织，改版的主要工作应集中在字体层级、空间关系和组件一致性。

### 推荐视觉方向

建议采用浅中性色页面、清晰的白色内容表面和有限的玫瑰色强调，保留用户现有主题选择。共享画面和白板保持足够的有效面积，背景图片只作为外围氛围，正文区域使用足够不透明的表面，以免降低阅读对比度。

| 设计项 | 建议起点 | 使用方式 |
| --- | --- | --- |
| 页面背景 | `#F7F8FA` | 作为所有主题的中性外层 |
| 内容表面 | `#FFFFFF` | 聊天、任务、云盘与对话框保持清晰边界 |
| 正文／次要文字 | `#252933`／`#626B7A` | 用于正文与时间信息，另行测量实际背景上的对比度 |
| 默认强调色 | `#B84775` | 用于主操作和选中状态，避免大面积着色 |
| 浅强调背景 | `#FAEEF3` | 小面积标签及选中面板，其他主题提供等价色阶 |
| 边框 | `#E4E7EC` | 分隔内容；可点击控件的边界需满足辨识要求 |
| 正文字号 | 14 至 16px，行高约 1.5 | 避免通过整体缩放补偿字号问题 |
| 圆角 | 控件 8px，面板 12px，对话框 16px | 用少量尺寸建立层级，避免每种组件独立取值 |

桌面宽屏继续使用共享区与侧栏两列，侧栏建议保持约 360 至 420px 的阅读宽度。中等宽度优先保证聊天文字和主要控制按钮可用，窄屏采用上下布局并保留固定的输入区域，避免将桌面界面整体缩成一小块。上述尺寸属于设计起点，应以 390px、768px、1440px 等实际视口检查结果调整。

具体实施时，先建立颜色、间距和文字样式的统一变量，再重做房间页上最常见的按钮与面板。随后将同样的规则应用到云盘、身份登录页及所有设置弹窗；聊天中的图片、语音和保存按钮应共享状态表达。最后清理被新规则取代的旧覆盖样式，检查自定义背景、四种强调色和键盘操作下的表现。

验收建议同时检查空列表与大量消息、较长中文文件名及任务标题，并确认移动端没有横向滚动，所有主要功能入口都能辨认。文本对比度以普通正文至少 4.5:1 为目标，控件和焦点状态不只依靠颜色区分；设计数值仍需对最终组合实际测量，不能仅凭色值列表宣称通过。

**处理状态：已调研未实现。** 本报告给出了单一推荐方向与实施顺序，本轮的图片、语音和保存按钮改动属于对应功能需求，不代表全站视觉改版已经完成。
