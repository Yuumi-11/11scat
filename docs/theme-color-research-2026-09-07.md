# 主题联动配色与自由选色调研及实施记录

日期：2026-09-07。本次针对“换主题色变化太小、只有雾蓝协调”与“恢复自由选色”的反馈，核查现有样式，读取公开设计资料后实施整套主题生成。此次修改接续任务卡高度与日期按钮调整，保持现有页面布局。

## 原因与调研依据

此前预设只替换 `--theme-accent`、`--theme-accent-dark` 和 `--theme-soft` 三项。页面、卡片和文字仍使用固定的蓝灰色，例如背景 `#f4f6f9`、正文 `#253247`、边框 `#dde3eb`；大面积表面不跟随选择变化，部分阴影与弹窗遮罩也有固定色相。外观设置仅渲染四个预设按钮，没有自定义颜色输入。

Radix Colors 按用途分配色阶：1–2 用于背景，3–5 用于组件状态，6–8 用于边框，9–10 用于实色操作，11–12 用于文字。这个分工适合当前项目，可以保持组件结构，改为由一份主题数据提供不同用途的颜色；本次没有直接安装 Radix 组件或复制其完整色板。[1]

MDN 对 OKLCH 的说明将颜色表达为明度、彩度和色相；调节明度和有限的彩度，可以在不同色相之间建立较接近的视觉层次。转换实现采用 Oklab 作者公开的线性 sRGB 转换矩阵，并在生成颜色超出 sRGB 色域时逐步降低彩度，避免直接截断通道造成明显偏色；最终输出普通十六进制值，不要求浏览器支持相对 OKLCH 语法。[2][3]

自由选色必须另行处理可读性。W3C 对普通文字规定至少 4.5:1 的对比度，对识别控件所必需的视觉信息规定至少 3:1；浅黄色适合配深色文字，不能给所有颜色固定套白字。Radix 同样明确列出 Yellow、Lime 等色阶需要深色前景，但其部分文字说明使用 APCA 数值，本项目的自动检查采用 WCAG 相对亮度公式，两套指标没有混用。[1][4][5]

## 实施方式

主题生成器以用户颜色为起点，在 OKLCH 中生成统一色相的页面背景、浅色内容表面和选中背景，正文与次要文字采用低彩度深色。装饰分隔线和交互边界分别使用不同变量，阴影与弹窗遮罩也随主题色相变化；大面积着色保持较浅，让任务和聊天内容可读。

用户选取的原色保留在颜色面板和输入框中，实际按钮颜色允许调整明度与彩度，并自动选择黑色或白色前景。正文在生成的主要表面上以 7:1 为目标，次要文字和强调文字以不低于 4.5:1 为目标，必要交互边界以不低于 3:1 为目标；悬停颜色也要通过相同组合的检查，不能只验证默认状态。

主题状态统一放在应用布局的 Provider 中，将颜色写入文档根节点。房间、登录页及通过 Portal 显示的新待办弹窗共享同一组变量，避免组件容器上的旧预设覆盖自定义颜色；浏览器支持时，其主题栏颜色也随设置更新。照片、视频与白板内容保持原色，成功、错误和录音状态仍保留各自含义。

外观设置保留四个带名称和选中标记的预设，新增原生颜色面板及十六进制输入，支持 `#RGB`、`#RRGGBB` 和省略井号的相同格式。无效输入显示提示且不替换当前主题，颜色选择可以即时应用；设置保存在当前浏览器，继续兼容旧版的预设名称，存储不可用时仍可在本次页面会话中换色。

## 验证与范围

生产构建及全部 14 项测试通过，其中 3 项为本次主题测试。颜色矩阵包含 RGB 每通道取 0、51、102、153、204、255 的 216 个组合，加上 4 个预设，共 220 个样本；逐一检查生成表面上的文字、按钮与悬停状态，以及交互边界的对比度，验证预设的各个主要配色用途确实随色相变化。

检查还覆盖颜色格式清理、非法输入、旧预设恢复、无效自定义设置回退，以及服务器默认 CSS 与生成器输出的一致性。首次检查发现中间亮度颜色配近黑色仍可能略低于 4.5:1，已经改为在纯黑与纯白之间选择，并增加悬停背景的验证；最终全部通过。相关文件 ESLint 无错误，保留 4 条既有原生图片优化建议。

上述结果属于生成色值、源码与构建验证，不代表所有浏览器、背景图片叠加及设备均已通过视觉或无障碍验收。本轮没有进行浏览器交互截图验收，原生选色面板的具体外观随浏览器和操作系统变化；登录页首次加载会先显示默认主题，再读取当前浏览器保存的选择，设置没有跨设备同步。
